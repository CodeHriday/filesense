Short answer (probable root cause)

The toggle UI is implemented as a clickable <div> with classes and role, and the component flips the header boolean by calling onHasHeaderChange(!hasHeader) inside handleToggleHeader. That part is fine. The most likely causes for the symptom (“can turn off but not on”) are either:

The parent onHasHeaderChange handler isn’t updating the hasHeader prop back to true (i.e., parent-controlled prop issue), or

UI/clickability is being blocked when header = false (e.g., another element overlays the toggle, or the toggle becomes disabled class / loses pointer events), or

Type/boolean mismatch so toggling !hasHeader sends true but parent treats it as falsy / a string and re-renders with a falsy value.

I’ll explain how to quickly identify which of these is happening, then give small fixes and a recommended robust implementation for the toggle.

Why the “off → on” pattern happens (detailed)
1) Parent not updating hasHeader (most common)

Your component is controlled: hasHeader is passed in, and clicking calls onHasHeaderChange(!hasHeader):

const handleToggleHeader = () => {
  if (isFixedWidthType || !onHasHeaderChange) return;
  onHasHeaderChange(!hasHeader);
};


If the parent’s onHasHeaderChange sets state incorrectly (or ignores true updates), the child will appear to not turn back on. Example mistakes in parent:

parent does setHasHeader(false) for both toggles accidentally

parent expects string 'true'/'false' and receives boolean true then coerces it to false

parent uses stale closure and doesn't update state (needs functional update)

How to check: add a console.log inside handleToggleHeader and also log props on render:

console.log('toggle clicked — hasHeader (before):', hasHeader);
onHasHeaderChange(!hasHeader);


If you see the click log but hasHeader prop does not flip on next render, it’s a parent/state handling issue.

2) Clicks being blocked or control disabled when off

CSS and rendering differences when hasHeader is false may cause:

an overlay element to appear above the toggle (e.g., .extended-fields-notice positioned absolutely) and block clicks

the .toggle-switch.disabled class applied (cursor not-allowed) or pointer-events removed

the toggle still visible but not receiving click events

From your CSS:

.schema-field-editor .header-toggle-row .toggle-switch.disabled { opacity: 0.6; cursor: not-allowed; } — this only applies when isFixedWidthType is true (your code adds disabled class only when isFixedWidthType). But some other CSS could be interfering when the UI flips to extended mode.

How to check (quick in browser console):

// Inspect the toggle DOM node:
const el = document.querySelector('.header-toggle-row .toggle-switch');
console.log('toggle classes:', el.className, 'pointer-events:', window.getComputedStyle(el).pointerEvents);


If pointerEvents is none or class disabled present unexpectedly, this explains the inability to re-enable.

3) Boolean vs non-boolean mismatch

If parent expects a particular type (e.g. 'true' / 'false') and you send true (boolean), parent logic may coerce/handle incorrectly and not set hasHeader to boolean true. You handle elsewhere showExtendedFields = isFixedWidthType || hasHeader === false — if hasHeader is undefined or 'false' string, hasHeader === false will be false, potentially causing unexpected UI state.

Check: console.log typeof hasHeader on render.

Suggested robust fixes

Below are two improvements — minimal quick fix and recommended more robust implementation.

Minimal quick fix (safe, non-breaking)

In your component change the onClick to always call the handler (instead of conditionally setting undefined). That removes possibility of undefined vs function confusion:

<div
  className={`toggle-switch ${hasHeader ? 'on' : 'off'} ${isFixedWidthType ? 'disabled' : ''}`}
  onClick={() => { if (!isFixedWidthType && onHasHeaderChange) onHasHeaderChange(!hasHeader); }}
  role="button"
  tabIndex={isFixedWidthType ? -1 : 0}
  ...
>


This guarantees handleToggleHeader logic is invoked in the same way for both directions.

Why this helps: it avoids accidental binding differences between true→false and false→true paths.

Recommended robust implementation (convert to accessible native input)

Replace the custom div-based toggle with a real checkbox input (hidden) + label styling. This makes toggling reliable and ensures onChange fires consistently.

Replace the toggle block with:

{/* Accessible toggle - uses native input */}
<label className={`toggle-switch ${isFixedWidthType ? 'disabled' : ''} ${hasHeader ? 'on' : 'off'}`} aria-pressed={!!hasHeader}>
  <input
    type="checkbox"
    checked={!!hasHeader}
    onChange={(e) => {
      if (isFixedWidthType) return;
      // ensure we pass a real boolean
      onHasHeaderChange && onHasHeaderChange(Boolean(e.target.checked));
    }}
    disabled={isFixedWidthType}
    style={{ display: 'none' }} // visually hide native checkbox
  />
  <span className="toggle-slider" />
  <span className="toggle-knob" />
</label>


And update CSS if needed (no changes required in most cases because your classes are already .toggle-switch.on / .off).

Benefits:

onChange is robust and fired for both mouse and keyboard consistently.

Browser accessibility and focus behavior are handled by native input.

Avoids weirdness if onClick is swallowed by overlay elements.

Extra defensive code you can add in parent (if you control it)

If parent uses setState based on previous value, prefer functional update to avoid stale closures:

// in parent
const [hasHeader, setHasHeader] = useState(true);
const handleHasHeaderChange = (value) => {
  setHasHeader(prev => {
    console.log('changing header from', prev, 'to', value);
    return !!value;
  });
};


This avoids race conditions.

CSS defensive tweak (prevent overlay / restore pointer)

If the toggle is being covered by another element when extended fields are shown, give the toggle a higher z-index and ensure pointer events are allowed:

.header-toggle-row { position: relative; z-index: 1; }
.header-toggle-row .toggle-switch { z-index: 2; pointer-events: auto; }


Add only for debugging if needed.
