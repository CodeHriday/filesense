Industry best practice for fine-grained enterprise access control follows a layered RBAC + ABAC hybrid model, with project-level containment, centralized policy enforcement, and auditable inheritance logic. Below is a distilled view of what leading organizations (AWS, Databricks, Snowflake, Fivetran, and DBT Cloud included) implement in production systems similar to your case.

1. Architectural Principle: “Policy as Data”
Best practice is to treat access rules as versioned, queryable metadata—not hard-coded logic in the application.
This enables integration, auditing, and delegated ownership.

Example:
Snowflake stores privileges in system catalogs (GRANT SELECT ON TABLE …) while Databricks enforces Unity Catalog policies centrally.
Your tool should store access policies as records (policy objects in DB), not embedded code checks.

2. Core Model: RBAC + Attribute Extensions (ABAC)
Most modern data platforms implement a hybrid:

RBAC (Role-Based Access Control): for broad operation rights by function (Admin, Engineer, Analyst).

ABAC (Attribute-Based Access Control): for fine‑grained decisions based on context — user attributes (department, region) + resource attributes (sensitivity, owner).

Why hybrid?
RBAC alone cannot scale to thousands of files or fields.
ABAC alone becomes non‑auditable.
Together, they give portability and traceable overrides.

Example Design:

Roles define allowed actions (e.g., “WRITE_MAPPINGS”, “READ_SCHEDULES”).

Attributes restrict scope (e.g., region='APAC', project='Retail', sensitivity='public').

3. Granularity Layers (Industry Reference Hierarchy)
Layer	Industry Practice	Governance Source
Workspace / Project	Logical container for all assets	Used by Snowflake DBs & Databricks Workspaces
Asset (File, Workflow, Mapping)	Resource‑level ACL	AWS S3 ACL, GCP IAM permissions on objects
Column / Attribute	Tag‑based policy (e.g., “PII: masked for analyst”)	Snowflake Dynamic Data Masking, Lakehouse Tagging
Row / Field‑Level conditions	Policy tables or view‑based filters	Row Access Policies (Databricks SQL, BigQuery)
Group / Role inheritance	Managed via IDP (Okta, IAM Groups)	Enforced with Just‑in‑Time sync
Recommendation:
Implement Project → Asset → Attribute hierarchy with inheritance; mirror the same principle in your metadata tables.

4. Ownership Boundaries and Permission Delegation
Responsibility	Best Practice
Admin	Set system defaults and manage role definitions, cannot access business data by default.
Project Owner / Creator	Controls asset‑level ACL, can delegate permissions within project scope.
User Group	Inherits project‑level role permissions. Used for onboarding/offboarding automation.
Individual User	Direct (explicit) permissions only when necessary; indirect via group is preferred.
Guideline: 80–90 % of permissions should come from group/project inheritance; < 10 % direct user overrides.

5. Implementation Pattern: Hierarchical Inheritance + Deny‑Override
Most enterprises adopt this decision flow:

Check explicit DENY (highest precedence).

Check user‑specific ALLOW.

Check group ALLOW (via IDP sync).

Check project/global default.

Default = DENY.

Framework references: AWS IAM Policy evaluation logic, OPA (Open Policy Agent) “deny > allow” precedence rule.

6. Data Storage of Policies
Best practice storage model aligns with three canonical tables:

Table	Purpose	Example Columns
policies	Defines unique rules	id, name, condition_expr, effect
assignments	Links (role/group ↔ resource)	policy_id, resource_id, subject_id
resource_catalog	Hierarchy metadata	id, type, project_id, parent_id
Evaluate via a policy engine (OPA, Casbin, AWS Lake Formation) rather than inline application code for scalability and auditability.

7. User Groups & IDP Integration
Standard practice is to delegate identity and group membership management to Identity Providers (IdP) such as AWS IAM, Okta, Azure AD, not your application directly.
Your system only caches the resolved group/role → permissions map.

Benefits:

Compliance alignment (SSO, SCIM sync)

Lifecycle automation (joiner/mover/leaver)

Single audit trail for security reviews

8. Why Projects Are Industry Standard
Yes — adopting Projects (also called Workspaces, Domains, or Tenants) is essential:

Containment boundary for assets, metadata, schedule, and permission inheritance.

Simplifies multi‑tenant access segmentation.

Enables project‑level billing or retention policies.

This aligns with data mesh and domain‑oriented ownership principles used across modern data platforms.

9. Summary – Recommended Enterprise Pattern
Design Element	Industry Consensus Practice
Access Control Model	Hybrid RBAC + ABAC
Containment	Project / Workspace model
Permission Evaluation	Hierarchical evaluation (deny‑override)
Policy Engine	Central engine (OPA / Casbin / internal metadata service)
Identity Source	Central IdP (e.g., Okta, IAM)
Auditing	Mandatory logging of “who viewed/edited what”
Attribute‑Level Security	Tag‑driven masking or view‑based filtering
User Groups	Functional groups synced via SSO/SCIM
UI Principle	Show inherited vs explicit access clearly
Granularity Scalability	Default from project → inherit → override only where needed
In concise terms:
Use “Project” as the top boundary, store policies as metadata managed via a policy engine, integrate with an IdP for roles/groups, and handle field‑level governance with tags and masking rules — this is today’s industry benchmark followed by Snowflake, Databricks, AWS Lake Formation, and most enterprise‑grade orchestration tools.
