# GOV - Data governance

## Summary
All 29 HTTP handlers are in server.js (L8602-8667, L8962-9824). There is also a service, `persistGovernanceMetadata` (backend/services/governanceService.js:29), which PROC calls, and a permission helper `hasTagPermission` (backend/services/columnAccessControl.js:69). The FE route /tag-management (src/pages/TagManagement.jsx) calls only `/api/governance-tags`. `/api/governance-policies` is used by src/pages/PolicyManagement.jsx. DataProfile.jsx also calls GOV endpoints: GET and POST `/api/files/:id/ownership` (src/pages/DataProfile.jsx:1198, :584), GET `/api/governance-tags` (:1229), GET `/api/governance-policies` (:1248), GET `/api/files/:id/columns/governance` (:1263) and PUT `/api/files/:id/sensitivity` (:2163).

Schema basis: where this note cites "prod dump" it means attached_assets/FileSence_prod_schema_Jan_05_1767956647766.sql. "Migration" means backend/migrations/*.js. The two disagree for `column_sensitivity_tags` (see B1).

Authentication has three patterns:
- Routes with explicit `authenticateToken`.
- `GET /api/files/:fileId/...` routes with no middleware of their own. They are covered because `app.use('/api/files', authenticateToken, schemaHistoryRoutes)` is registered earlier (server.js:5283) and runs for every path under /api/files. This holds only if that registration succeeded; it sits inside a try/catch (server.js:5278-5285). On the JWT-only /api/files routes this prefix `authenticateToken` runs in addition to the per-route `authenticateToken`, so the user and permission lookup runs twice.
- `GET /api/governance-policies*` and `GET /api/governance-tags*`, which have no authentication at all.

Authorisation is inconsistent. It uses three different checks: a `file_governance:write` permission, a `policies:write` permission, and `requireAdmin`. Several write routes check nothing beyond a valid login. The `file_governance:write` and `policies:write` checks are exact string matches against a `req.user.permissions` array that mixes strings and objects (see S6). `policies:write` is seeded for Admin and Data Steward; `file_governance:write` is granted nowhere in the repo (see B12).

GET responses are cached 300s per user (`cache:<userId|anonymous>:<url>`) (backend/middleware/cacheMiddleware.js:19-23, :31).

## Entry points
Common: `authenticateToken` = backend/src/middleware/authenticate.js:17 (not traced). `requireAdmin` = server.js:5417, which calls `userHasAdminAccess` (server.js:380). That function accepts role Admin/admin (server.js:384-391), or one of exactly two permissions, `users:write` and `roles:write` (server.js:397-400). `hasTagPermission` does not use that function. It uses a second `userHasAdminAccess` from backend/utils/permissionHelpers.js (imported at columnAccessControl.js:11), whose list is `users:write`, `roles:write` and `project_management:write` (permissionHelpers.js:85-89). So a user holding only `project_management:write` passes the column tag POST checks but fails `requireAdmin`. The column policy POST computes `isAdmin` with the server.js version (server.js:9692) and then calls `hasTagPermission` (the helper version) per tag (:9699). Errors are 500 with a generic message unless stated.

Cache invalidation: the `invalidateCache(pattern)` middleware used on most write routes runs before the handler, hence before the DB write (backend/middleware/cacheMiddleware.js:99-113). A GET arriving between the invalidation and the write can re-cache the old data.

### File ownership
- GET /api/files/:fileId/ownership (server.js:8602). Auth: implicit (see Summary). Returns the `file_ownership` row. 404 `No ownership record found for this file` if there is none (:8611-8613).
- POST /api/files/:fileId/ownership (:8623). Auth: JWT only, no permission or ownership check. Body `owner_name, owner_email, owner_contact`, no validation. Upserts on `file_id` and sets `owner_user_id = req.user.id`, so every POST overwrites the owner with the caller (:8629-8634). Invalidates `cache:*:*ownership*`. Returns the row with 200.
- PUT /api/files/:fileId/ownership (:8645). Auth: JWT only. Updates name, email and contact. Does not change `owner_user_id`. 404 `Ownership record not found` (:8658).
- PUT /api/files/:fileId/sensitivity (:9417). Auth: JWT only, no permission check. Requires `sensitivity_level` (400), which must be one of `['Public','Internal','Confidential','Restricted']` (:9427). If no `file_ownership` row exists it inserts one with `owner_user_id = req.user.id` (:9440-9446). Otherwise it updates the existing row. The file's existence is not checked beyond the FK (an FK failure would return 500). The cache invalidation pattern is `cache:*:*files*`.

### Column sensitivity tags (table column_sensitivity_tags)
- GET /api/files/:fileId/columns/sensitivity-tags (:8962). Implicit auth. All rows for the file, ordered by `column_name`.
- GET /api/files/:fileId/columns/:columnName/sensitivity-tag (:8979). Implicit auth. 404 if absent. `columnName` is not URL-decoded here (Express decodes route params itself).
- POST same path (:9000). Requires `req.user.permissions` to include `file_governance:write`, else 403 (:9003). The level is `req.body.sensitivity_level || req.body.classification_level` (legacy alias) (:9012). It is required (400) and must be one of `['Public','Internal','Confidential','Restricted','PII']` (:9019). Upserts on `(file_id, column_name)` and records `tagged_by = req.user.username || 'user'` (:9030). Invalidates the file cache and `cache:*:*sensitivity*`.
- DELETE same path (:9046). JWT only, no permission check (inconsistent with POST). 404 if absent. Returns `{message, tag}`.

### Governance policies (table governance_policies)
- GET /api/governance-policies (:9074). No auth. All policies, `ORDER BY created_at DESC`.
- GET /api/governance-policies/:policyId (:9088). No auth. 404 `Policy not found`.
- POST /api/governance-policies (:9109). Requires `policies:write` (403, :9112). `policy_name` is required (400). `policy_id = uuidv4()` (:9126). `rules` is stored as JSON, default `{}` (:9132). Returns 201. A 23505 error returns 409 `Policy ID already exists`.
- PUT /api/governance-policies/:policyId (:9146). Requires `policies:write`. Overwrites name, description and rules unconditionally (:9159-9165). `policy_name` is NOT NULL (createDataGovernanceTables.js:57; prod dump :5077), so a body without `policy_name` makes the UPDATE raise 23502 and the handler returns a generic 500 with nothing written. Only the nullable fields (description) are overwritten with null, and `rules` falls back to `{}`. 404 if not found. Invalidates `cache:*:*policies*` only (see B13).
- DELETE /api/governance-policies/:policyId (:9179). Requires `policies:write`. 404 if not found. Returns `{message, policy}`. In the prod dump the FKs from `file_policy_assignments` (fk_policy_assignment_policy, dump :7458) and `column_policy_assignments` (fk_column_policy_policy, dump :7400) to `governance_policies` are ON DELETE CASCADE, so deleting a policy silently removes all its file and column assignments.
- Rule content (`retention_days`, `access_control`, `encryption_required`) is defined only by the FE (see GRP.md:189). The server stores it opaquely.

### File policy assignments (file_policy_assignments)
- GET /api/files/:fileId/policies (:9210). Implicit auth. Join with policy fields, `ORDER BY assigned_at DESC`.
- POST /api/files/:fileId/policies (:9231). Requires `file_governance:write`. `policy_id` is required (400). Upserts on `(file_id, policy_id)` and refreshes `assigned_at` (:9251). Returns 201. FK error 23503 returns 404 `Policy not found`; the same code is also raised for a non-existent file, so the message is misleading.
- DELETE /api/files/:fileId/policies/:policyId (:9268). Requires `file_governance:write`. 404 if the assignment is absent.

### Governance tags (governance_tags)
- GET /api/governance-tags (:9301) and GET /api/governance-tags/:tagId (:9315). No auth. 404 `Tag not found`.
- POST /api/governance-tags (:9336). `authenticateToken` + `requireAdmin`. `tag_name` is required (400). `tag_id = tag_<Date.now()>_<5 random bytes hex>` (:9344). Defaults are `color '#3B82F6'` and `badge_style 'default'` (:9350). Returns 201. 23505 returns 409 `Tag name already exists`. `permission_level` and `sensitivity_level`, which the FE sends, are not read (:9338).
- PUT /api/governance-tags/:tagId (:9364). Admin. Overwrites name, description, color and badge_style with whatever is in the body. `tag_name` is NOT NULL and UNIQUE (createGovernanceTagsTables.js:14; prod dump :5095), so a body without `tag_name` makes the UPDATE (:9369-9375) raise 23502. The handler maps only 23505 to 409, so 23502 returns a generic 500 and nothing is written. The other fields (description, color, badge_style) are overwritten with the body value, so omitted ones become null if the columns are nullable. 404 or 409 as above. Invalidates `cache:*:*tags*` only (see B13).
- DELETE /api/governance-tags/:tagId (:9392). Admin. 404 if absent. Returns `{message, tag}`. In the prod dump the FKs to `governance_tags` from `file_tag_assignments` (fk_tag_assignment_tag, dump :7500), `column_governance_tag_assignments` (fk_column_tag_tag, dump :7389) and `tag_permissions` (fk_tag_permission_tag, dump :7760) are ON DELETE CASCADE, so deleting a tag silently removes all its file and column assignments. Invalidates `cache:*:*tags*` only (see B13).

### File tags (file_tag_assignments)
- GET /api/files/:fileId/tags (:9748). Implicit auth.
- POST /api/files/:fileId/tags (:9769). Requires `file_governance:write`. `tag_id` is required. Upserts and returns 201. 23503 returns 404 `Tag not found`.
- DELETE /api/files/:fileId/tags/:tagId (:9806). JWT only, no permission check (the POST requires one). 404 if absent.

### Column governance tags and policies
- GET /api/files/:fileId/columns/governance (:9470). Implicit auth. Batch endpoint. Returns `{tags:{col:[...]}, policies:{col:[...]}}` (:9527). This handler does not apply tag-permission filtering. Read filtering exists elsewhere (see S4).
- GET /api/files/:fileId/columns/:columnName/tags (:9538). Implicit auth. Applies `decodeURIComponent` to a param Express has already decoded.
- POST same path (:9559). JWT only. `tag_ids` must be an array (400). Replace semantics: it computes tags removed and tags added against the current set. For each tag removed or added the caller must satisfy `hasTagPermission(user, tag_name, 'edit')` (:9587, :9604), else 403. `hasTagPermission` returns true for admin (permissionHelpers.js version, see Common); otherwise it needs the literal permission `tag:<lowercased name>:edit` (columnAccessControl.js:78), matched against string entries or object entries (`p.name` or `resource:action`, :81-88). The 403 message says `:edit or :write`, but only `:edit` is checked. After the checks it deletes all assignments for the column and inserts the new ones in a single multi-row statement with no transaction (:9614-9629). Tag ids are not validated in advance, and duplicates in `tag_ids` are not removed. An unknown id (FK, 23503) or a duplicate id (unique, 23505) makes the INSERT fail with a generic 500 after the DELETE has already run, leaving the column with no tags. Invalidates the cache via `invalidate` imported from backend/middleware/cacheMiddleware: `cache:*:*<fileId>*` and `cache:*:*tags*` (:9633-9635), after the write.
- GET /api/files/:fileId/columns/:columnName/policies (:9649). Implicit auth.
- POST same path (:9670). JWT only. `policy_ids` must be an array (400). Non-admin callers need `hasTagPermission(..., 'edit')` for every tag on the column (:9698). If the column has no tags, only admins may assign (403 `Required: Admin privileges.`, :9709). It then deletes all column policy assignments and re-inserts (:9718-9733), again with no transaction. An empty `policy_ids` removes all, and is subject to the same permission check. Duplicate or unknown ids in `policy_ids` fail the INSERT (23505 or 23503) with a generic 500 after the DELETE has run (:9738-9739). The route invalidates only `cache:*:*policies*` (:9670), before the handler. The batch GET `/columns/governance` URL does not contain "policies", so its cached response stays stale for up to 300s.

### Service-level behaviour: persistGovernanceMetadata (governanceService.js:29)
Called after profiling (see PROC.md:395). One DB transaction (BEGIN at :50, COMMIT at :234, ROLLBACK at :249).
1. Updates `files.contains_pii` and `files.data_classification` only when provided (:58-66).
2. Deletes ALL `file_tag_assignments` for the file, including ones assigned manually via the API (:90). It then upserts a `governance_tags` row per tag name, with id `tag_<lowercased name with non [a-z0-9_] replaced by _>`, colour `#3B82F6`, and description "Auto-generated tag for X" (:100-110). Existing tag descriptions are overwritten on conflict (:108). The conflict target is `tag_name` only (:107), so two names that map to the same id (for example "Foo Bar" and "foo_bar") with different `tag_name` raise a primary-key violation (23505) that is not covered. The whole transaction is then rolled back and `success:false` is returned.
3. Deletes all `column_sensitivity_tags` for the file (:141). Each PII column is inserted with `sensitivity_level 'PII'` and `data_type 'string'` (:158-164); this INSERT does not write `tagged_by` or `tagged_at`. A per-column failure is caught and ignored (:170-177).
4. Deletes all `column_governance_tag_assignments` for the file, including manual ones (:194). It creates or reuses the PII tag (`tag_pii`, `#EF4444`, `destructive`) and assigns it to each PII column (:204-217).
5. Returns `{success:false, error}` on failure and does not throw (:257-261).
`normalizePiiColumns` (:279) accepts strings or objects with `column_name` or `name`. When a profiled schema is given, names not found in it (case-insensitive) are skipped (:301-309). It throws if a profiled schema entry has no `name`.
The service writes invalidate no cache.

## Flags
SECURITY
- S1. GET /api/governance-policies, GET /api/governance-policies/:id, GET /api/governance-tags, GET /api/governance-tags/:id have no authentication (server.js:9074, :9088, :9301, :9315). The cache key for these is `anonymous` when `req.user` is unset (cacheMiddleware.js:22).
- S2. Any logged-in user can POST or PUT file ownership (:8623, :8645) and PUT file sensitivity (:9417), DELETE a column sensitivity tag (:9046), and DELETE a file tag (:9806). Compare the permission checks on the sibling POST routes. The ownership POST also reassigns `owner_user_id` to the caller.
- S3. Column tag and column policy POSTs (:9559, :9670) rely on `hasTagPermission` only. Column policy assignment by a non-admin also needs edit rights on all the column's tags. There is no `file_governance:write` check and no check of project or file access (`checkFileProjectAccess` in columnAccessControl.js:35 is not called by these handlers).
- S4. The GOV GET endpoints (the batch `/columns/governance` at :9470 and the column tag/policy GETs) return tag and policy data without tag-permission filtering. Read-level filtering does exist in other code: `filterDataset` (server.js:1977) and `filterColumns(req.user, columnGovernance, 'read')` (server.js:6444, :6622), implemented at columnAccessControl.js:154-186. It treats a tag as sensitive when `sensitivity_level` is `restricted` or `private`, or when `requires_view_permission` (read) or `requires_edit_permission` (edit) is set (:166-171), and then requires `hasTagPermission` for every sensitive tag (:184-186).
- S5. The 'implicit-JWT' routes depend on the registration at server.js:5283 inside a try/catch. If it fails to load, they would be unauthenticated.
- S6. Permission shape mismatch. `req.user.permissions` starts with three strings (`dashboard:read`, `file_profile:read`, `quality_checks:read`, authenticate.js:218-222), then gets objects `{name, resource, action}` from the `role_permissions` join (:240-246), then whatever entries are in the role's JSON `permissions` column (:277-282). `[...new Set()]` does not dedupe objects (:290). The handler checks use `permissions.includes('file_governance:write')` or `includes('policies:write')` (server.js:9003, :9112, :9149, :9182, :9234, :9271, :9772). That is an exact string match and never matches the object form. These checks therefore pass only when the role's JSON column holds the string entry. `hasTagPermission` handles both forms (columnAccessControl.js:81-88). Permissions are cached 600s (authenticate.js:293-295).

BUG
- B1. Schema drift for `column_sensitivity_tags`, not a prod bug. The migration creates `classification_level VARCHAR(50) NOT NULL` with no `sensitivity_level`, `tagged_by` or `tagged_at` (createDataGovernanceTables.js:39). The prod dump (FileSence_prod_schema_Jan_05_1767956647766.sql:4508-4521) has `sensitivity_level NOT NULL`, `tagged_by`, `tagged_at`, and `classification_level DEFAULT 'unclassified' NOT NULL`, which is why inserts that omit `classification_level` succeed. It also has index `idx_column_tags_classification` on `sensitivity_level` (dump :4522). Nothing in backend/migrations adds the extra columns (grep for `tagged_by` hits only the handler, the service, transformationProfilingService.js:672 and migrateColumnSensitivityToGovernance.js:40, :57, which reads them). So a database built only from migrations would break the handlers (server.js:9025), the service and the migration script; prod was evidently altered outside the migrations. Only the handler (server.js:9025-9028) and transformationProfilingService.js:672-676 write `tagged_by`/`tagged_at`.
- B2. The 403 text for column tags says `tag:x:edit or tag:x:write` (:9589), but only `:edit` is checked (columnAccessControl.js:78).
- B3. Column tag and policy POSTs delete and then insert without a transaction (:9614-9629, :9718-9733). A failing insert (unknown id, duplicate id in the request) leaves the column with no assignments and returns a generic 500. The assignment tables have unique constraints `unique_column_tag` and `unique_column_policy` (createColumnGovernanceTables.js:26, :48), which is what makes duplicate ids fail.
- B4. `persistGovernanceMetadata` wipes manually assigned file tags and column PII assignments on every run (:90, :194). Manual tags via the API are lost on the next profiling run.
- B5. In the service, a per-column insert failure is swallowed (:170) inside a Postgres transaction. After an error Postgres aborts the transaction, so later statements and the COMMIT would fail and the whole result would be a rollback. The catch therefore cannot achieve its stated intent ("Don't fail entire governance persistence").
- B6. Tag `permission_level` from TagManagement.jsx (:55-56, :87-88, :330-339) is never persisted by POST or PUT (server.js:9338, :9367); there is no such column. `sensitivity_level` is also not written by those handlers, but the column exists on `governance_tags` with default `'public'` (addTagPermissionLevels.js:17), so `SELECT *` returns the lowercase DB value or the seeded value, not the FE's `Low`/`High`/etc. scale. The seed (backend/migrations/seedGovernanceTags.js) is the only code that sets `sensitivity_level`, `permission_required` and the view/edit flags. It inserts 5 tags (insert at :95-108):
  - `tag_pii` (PII): sensitivity `restricted`, permission_required `pii`, view true, edit true (:20-28).
  - `tag_confidential` (Confidential): `restricted`, `confidential`, view true, edit true (:31-39).
  - `tag_internal` (Internal): `private`, `internal`, view false, edit true (:42-50).
  - `tag_public` (Public): `public`, permission_required null, view false, edit false (:53-61).
  - `tag_restricted` (Restricted): `restricted`, `restricted`, view true, edit true (:64-72).
- B7. PUT on tags and policies overwrites all fields with the request body (:9157-9164, :9367-9374). A missing `policy_name` or `tag_name` is not stored as null: both columns are NOT NULL, so the UPDATE raises 23502 and the handler returns a generic 500 with no write. Only the nullable fields are overwritten with null or the default.
- B8. Cache invalidation after a column sensitivity tag change does not clear the cached GET responses by file. `invalidateFileCache(fileId)` (server.js:9035) calls `invalidateCachePattern('GET:/api/files/<id>*')` (backend/src/middleware/cache.js:152-153), which uses the `cache` object from backend/config/redis.js (cache.js:5; delPattern at config/redis.js:155). The GET cache keys are `cache:<user>:<url>` (cacheMiddleware.js:23) in a different store, `cacheService` (own Redis client and NodeCache, cacheService.js:17-18, :75; delPattern at :155). The two stores are separate and the pattern `GET:/api/files/...` cannot match a `cache:...` key, so `invalidateFileCache` has no effect on them. The extra `invalidateCachePattern('cache:*:*sensitivity*')` (:9036) also goes through the config/redis store, not `cacheService`, so it does not clear the GET responses either. (The `invalidateCache` middleware and `invalidate` imported from cacheMiddleware.js do use `cacheService`.)
- B9. The 23503 handler on file policy and file tag assignment says "Policy/Tag not found" for any FK failure, including a missing file (:9260, :9798).
- B10. The `invalidateCache` middleware clears the cache before the handler writes (cacheMiddleware.js:99-113), so a concurrent GET can repopulate stale data. The column policy POST does not invalidate the `/columns/governance` batch cache (see the column policies entry above).
- B11. The service's deterministic tag id can collide with an existing tag's primary key under a different `tag_name`, which rolls back the whole persist (governanceService.js:100, :107). `tag_id` is the primary key and `tag_name` is separately UNIQUE (createGovernanceTagsTables.js:14), so the `ON CONFLICT (tag_name)` target does not cover a `tag_id` clash.
- B12. `file_governance:write` is granted nowhere in the repo: no seed, migration or FE file contains it. The only occurrences are the four checks in server.js (:9003, :9234, :9271, :9772). Those handlers have no admin bypass, so by default nobody passes column sensitivity tag POST, file policy POST and DELETE, and file tag POST, not even Admin. Production data could differ from the repo (a role edited by hand or through the roles UI).
- B13. Tag PUT and DELETE invalidate only `cache:*:*tags*` (server.js:9364, :9392), and policy PUT and DELETE only `cache:*:*policies*`. The batch URL `/api/files/:id/columns/governance` contains neither "tags" nor "policies", so after a tag rename or delete, or a policy change, the batch response stays stale for up to 300s.

DUPLICATE
- D1. Two sensitivity-tag models for columns: `column_sensitivity_tags` (level text, including `PII`) versus `column_governance_tag_assignments` plus `governance_tags`. The service writes PII to both (governanceService.js:164, :214). The migration backend/migrations/migrateColumnSensitivityToGovernance.js:40 migrates from the first to the second.
- D2. Sensitivity level lists differ by endpoint. File-level has 4 values (:9427) and column-level has 5, including `PII` (:9019). `governance_tags.sensitivity_level` uses lowercase `public/restricted/private` (addTagPermissionLevels.js:26). The FE uses `Low` (TagManagement.jsx:56).
- D3. Four admin checks: `requireAdmin` (server.js:5417), `userHasAdminAccess` in server.js (:380, two permissions), `userHasAdminAccess` in backend/utils/permissionHelpers.js (:80, adds `project_management:write`, used by `hasTagPermission`), and FE `hasPermission('governance_tags:write') || hasPermission('users:write') || roles.includes('Admin')` (TagManagement.jsx:60). ## Domain terms
- Sensitivity level, classification level, data classification: the same concept under different names (`sensitivity_level`, `classification_level`, `files.data_classification`).
- Governance tag versus sensitivity tag versus PII tag.
- Governance policy (rules: retention_days, access_control, encryption_required) versus quality rules (a different area) versus `/api/policies` (GRP).
- Ownership: file_ownership with owner_user_id, name, email, contact (and creator_* in prod).
- Permission level (Public/Private/Restricted in the FE, TagManagement.jsx:229-231) versus tag permission (`tag:<name>:read|edit`).
- Admin access: Admin role or admin-equivalent permissions (two or three, depending on which function).
- Column governance versus file tag.
