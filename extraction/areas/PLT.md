# PLT - Platform bootstrap and infrastructure

## Summary
Two processes in production on Replit: `productionBootstrap.js` owns the public port and proxies to `server.js` (the monolith API) once ready (.replit:9; productionBootstrap.js:14-17). `server.js` builds the Express app (middleware, ~14k lines of routes), binds the port first and initialises the DB afterwards (server.js:14053-14066). A Python service `profile_api.py` is spawned after readiness (productionBootstrap.js:147-148). A second deploy path exists: GitHub Action to EC2 with pm2 (prod-deployment.yml). A second, apparently unused app lives in `backend/src/` (app.js, server.js).

## Entry points

### 1. productionBootstrap.js (Replit deploy run command)
- Trigger: `.replit` `run = ["node","productionBootstrap.js"]` (.replit:9); build is `npm run build` = `vite build` (.replit:10; package.json:7).
- Auth: none. Listens on `PORT || 5000`, host `0.0.0.0` (productionBootstrap.js:14, :134).
- Behaviour: spawns `node --max-old-space-size=512 --expose-gc server.js` with `NODE_ENV=production`, `PORT=INTERNAL_API_PORT || PORT+1` (:15, :49-57). Polls every 500 ms `/api/health/live` then `/api/health/ready` on the internal port, 2000 ms timeout each (:67-89, :139-151). Ready only on HTTP 200.
- Before ready: `GET /` and `/api/health/live` return 200 text "Application is starting"; everything else 503 JSON with `Retry-After: 5` (:96-108). The `/` check is an exact string match on `req.url`, so `/?x` gets 503. WebSocket upgrades are destroyed before ready (:123-127).
- After ready: starts `python profile_api.py` once with `PROFILE_API_PORT` (default 8000), `BACKEND_API_URL=http://127.0.0.1:<publicPort>`, `DISABLE_VIRUS_SCAN` defaulting to `'true'` (:33-39, :148). Proxies all HTTP/WS with `xfwd` (:18, :111). `NODE_ENV=production` is forced for the API child only (:52). Because `BACKEND_API_URL` points at the public bootstrap port (:37), Flask-to-API calls go through the proxy and the general rate limiter.
- Errors: proxy error returns 502 `{error:'Application is temporarily unavailable.'}` (:115-120). If the API process exits while not shutting down, the bootstrap exits with its code or 1 (:59-62). Profile API exit is only logged, not restarted (:43-45).
- SIGTERM/SIGINT: kill both children, close server, exit 0 (:156-169).
- Note: once ready, the bootstrap never re-checks readiness (interval cleared :150).

### 2. server.js startup (`startServer`)
- Trigger: module load calls `startServer()` (server.js:14216); dev command `NODE_ENV=development node --max-old-space-size=512 --expose-gc server.js` (.replit:54), `npm run dev:backend` (package.json:9).
- Order: create `http.createServer(app)` and listen on `PORT || (production ? 5000 : 3000)`, `0.0.0.0` (server.js:107, :14053-14054); `initializeDatabase()` (:14066) which calls `database.initialize()` = `testConnection()` with 5 retries, 1000 ms initial delay, doubling (backend/config/database.js:171, :343-350; di/bootstrapper.js:137-141), then `initializeTables()` creating/altering the `transformations` table (database.js:286-325).
- Then `repairBootstrapAdminRoles` and `getDashboardPrerequisiteStatus` (server.js:14073-14074). `getDashboardPrerequisiteStatus` is the local name of `getPrerequisiteStatus`, imported by destructuring rename (server.js:5878-5881). Rule: if user `username='admin'` has no `user_roles` rows, insert roles `Admin`, `Vendor Manager`, `Governance Manager` (repairCleanPublishDashboardPrerequisites.js:3, :5-22). Readiness requires only tables `project_members`, `access_group_members`, `project_access_groups`; missing function `get_user_projects(integer)` is a warning only and the app uses a "built-in fallback" (:27-56; server.js:14094-14096). If not ready, `app.locals.databasePrerequisites.ready=false` and the API stays up but `/api/health/ready` returns 503 (server.js:14076-14086, :1180-1189).
- Fatal path: `repairBootstrapAdminRoles` rethrows on error (repairCleanPublishDashboardPrerequisites.js:70-76), and `getPrerequisiteStatus` throws if `users`, `roles` or `user_roles` are missing. Both calls sit inside the `startServer` try, so either leads to `process.exit(1)` (server.js:14196-14211); the bootstrap then also exits (productionBootstrap.js:59-62).
- Then: `initBusinessProcessTables` (errors logged, continue, :14100-14106); start scheduler worker (:14111); log whether `ENCRYPTION_KEY` is 64 hex chars, warning only, never fails (:14117-14131); start BullMQ upload worker with concurrency 5, failure only warns (:14135-14144); Socket.IO with CORS from the same allowedOrigins, methods GET/POST (:14148-14169); visual mapping WebSocket init (:14172); materialized view worker every 60 s (:14178); orphaned-job recovery (:14187).
- Module-load migration IIFE (server.js:5884-5956): an un-awaited async IIFE that runs at module load, concurrently with `startServer`. It runs about 60 `migrationTracker.runOnce(...)` migrations in sequence (:5886-5945), including `createProjectsAndGroups` (:5908), then `ensureFileUploadPermissions(dbPool)` on every start, untracked (:5948), then a raw `ALTER TABLE transformation_jobs ADD COLUMN IF NOT EXISTS jira_issue_key VARCHAR(50)` (:5950). Any throw is caught, logged, and aborts the remaining migrations (:5953-5955). Nothing orders it against the prerequisite check at :14074 (see Flags UNCLEAR).
- Workers started at module load, before DB init: file worker `.start()` (:45), upload cleanup (max age 3600000 ms, orphaned uploads under `__dirname/uploads`; runs `cleanup()` at start and then every `15*60*1000` ms, uploadCleanupWorker.js:17-25) (:55-60), SLA monitor 900000 ms (:63-68), insights aggregation at `'02:00'` (:71-75), retention at `'01:00'` (:78-83). Time zone of the 01:00 and 02:00 workers: the trigger compares `now.getHours()` (server local time) against the target hour (insightsAggregationWorker.js:60; retentionPolicyWorker.js:71), but the once-per-day guard uses the UTC date from `toISOString().split('T')[0]` (insights :63; retention :73). Insights dedupes through `MAX(metric_date)` in the database (insights :77); retention keeps `lastRunDate` in memory only (retentionPolicyWorker.js:25, :75-77), so a restart in the 01:xx hour re-runs it.
- Failure: any exception in startServer logs troubleshooting text and `process.exit(1)` (:14196-14211).
- Process-level handlers: none. A grep for `uncaughtException` and `unhandledRejection` across the JS files finds no match, so a stray rejection or exception is handled by the Node default.
- Shutdown: SIGTERM/SIGINT run `gracefulShutdown` stopping workers and closing DB, exit 0 or 1 (:14219-14269). It does not close the HTTP server or Socket.IO; `httpServer` is local to startServer.
- Config load can kill the process earlier: `backend/src/config/environment.js` is required at server.js:120 and runs `validateConfig()` at require time (environment.js:138). In production it throws on missing `JWT_SECRET` (:62-71), a weak or under-64-char secret (:95-103), or any storage-provider issue (`s3` without `AWS_ACCESS_KEY_ID`, `azure` without connection string, `google` without `GOOGLE_APPLICATION_CREDENTIALS`) (:115-134). The API child dies and the bootstrap exits (productionBootstrap.js:59-62).

### 3. server.js global middleware chain (cross-cutting for all routes)
Registration order in the file (routes are registered synchronously at module load between these points):
- `app.set('trust proxy', 1)` (:110).
- Helmet + CSP: NOT in this position in practice. It is registered inside an async IIFE after `await getAllSecretData()` (:435-494), so `app.use(helmet)` runs after all synchronous module-level registration, including every route, the 404 handler and `errorHandler` (:14030-14041). See Flags BUG. When it runs: CSP `scriptSrc 'self' 'unsafe-inline'`, HSTS `maxAge 31536000` includeSubDomains preload, `frameAncestors 'none'`. In production the Okta domain comes from the secrets store (`secrets.OKTA_DOMAIN`), otherwise from `VITE_OKTA_DOMAIN || OKTA_DOMAIN` plus localhost connect-src (:444-451).
- compression level 6, threshold 1024, skipped if header `x-no-compression` is present (:499-510).
- CORS: origins from `ALLOWED_ORIGINS` (comma split) else default list `localhost:5000, localhost:3000, https://*.replit.dev, https://*.replit.app, https://filesense.blumetra.com` (:513-515). `*` entries converted by `globToRegex`. No Origin header is allowed. Methods `GET, POST, PUT, DELETE, OPTIONS` (PATCH not listed), headers `Content-Type, Authorization, X-Requested-With`, credentials true, preflight 204 (:517-555). Disallowed origin gives `Error('Not allowed by CORS')` passed to the error handler (:547); that is an untyped error, so the default branch returns 500 `INTERNAL_ERROR`, not 403 (errorHandler.js:85-101). `.replit` sets `ALLOWED_ORIGINS` including filesense-qa.blumetra.com and filesense.blumetra.com (.replit:97).
- Body parsers JSON and urlencoded, limit `50mb` (:556-557).
- Production only: `GET /` serves `dist/index.html`, or a 200 "Application is starting" shell if the file is missing (:573-589).
- express-session: secret `SESSION_SECRET || JWT_SECRET`, `secure` in production, httpOnly, maxAge 24 h, in-memory default store (no store configured) (:593-602).
- Audit middleware for all requests (:606); `extractFileId` (:609).
- Timeouts: request 30000 ms returns 408 `{error:'Request timeout'}`; response 35000 ms returns 408 if headers not sent and destroys the socket (:612-640).
- Rate limits: `generalLimiter` mounted on `/api/` (:767): 15 min window, max 500, 429 JSON, skips `/health/ready` and `/health/live` (:643-664). `authLimiter`: 5 per 15 min, skipSuccessfulRequests, applied to login, register, request-password-reset (:667-682; :10417, :10513, :10830). `uploadLimiter`: 20 per hour per IP (:685-698), applied to check-duplicate, upload, drop (:2489, :2557, :3476). The file status endpoint is registered before the general limiter on purpose (:700-703).
- After all routes: production-only `/profile-api` proxy. A preceding middleware calls `req.setTimeout(0)` and `res.setTimeout(0)`, so the 30 s and 35 s timeouts above do not apply to it (server.js:13974-13982; the comment at :13974 says AI calls can take 60-90 s). `/profile-api` is not under `/api/`, so the general limiter (mounted on `/api/`, :767) does not cover it and it is not rate limited. Proxy target `http://localhost:<PROFILE_API_PORT||8000>`, `proxyTimeout 120000`, path rewrite, body re-serialised for POST/PUT/PATCH, 502 `{error:'Profile API unavailable'}` on error (:13973-14004); no `authenticateToken` precedes it in this block (see SECURITY). Static `dist` and SPA fallback for non-`/api` paths (:14007-14023). 404 handler builds `NotFoundError('Route <url> not found')` (:14030-14037); then `errorHandler` (:14041). The Helmet registration from the async IIFE lands after these.
- Error handler: JWT errors give 401 `AUTHENTICATION_FAILED`; Multer `LIMIT_FILE_SIZE` gives 400 `FILE_TOO_LARGE`; default 500 `INTERNAL_ERROR` with message hidden in production (errorHandler.js:62-101). Error shape `{error:{message,code,timestamp,details}}`. Error detail for other error types is in ERR/SEC areas.

### 4. Health endpoints (server.js)
- `GET /health-check` returns 200 `{status:'ok',timestamp}` (:1027). `GET /api/health` same (:1033). Also `app.use('/api/health', healthCheckRoutes)` (:1038-1039), traced below.
- `healthCheckRoutes` (backend/routes/healthCheckRoutes.js):
  - Router `GET /` (:31-50) would report the upload queue through BullMQ `getJobCounts` (:13-26), returning 200 `healthy`/`degraded`. It is shadowed by `app.get('/api/health')` at server.js:1033, which is registered first, so it is never reached.
  - `GET /api/health/python` (:55-77): no auth. Spawns `python3 -c <inline script>` on every request (:85). Checks the five packages openpyxl, pandas, pyarrow, ijson, defusedxml (:112-118). All installed gives 200 `healthy`; otherwise 503 `degraded`. The route has a catch that returns 500 `unhealthy` (:71-76), but it is unreachable in practice: `checkPythonEnvironment` only ever resolves (non-zero exit, parse failure and spawn error all call `resolve`, :140-166). On non-zero exit the result includes raw `stderr` (:140-146); on JSON parse failure it includes raw `stdout` (:152-156); spawn failure includes the error message (:161-165). All are returned in the 503 body.
- `GET /api/health/db`: 200 healthy or 503 unhealthy using `database.getHealthStatus()` (:1042-1064).
- `GET /api/health/enterprise`: checks db, cache, queue (`file-processing`), materialized views, memory (MB), uptime; `?detailed=true` adds DB stats; 200 `healthy` or 503 `degraded`; only a database failure sets degraded (cache/queue/view failures leave `overallHealthy` true) (:1069-1169). Version `APP_VERSION || '1.0.0'`.
- `GET /api/health/ready`: 503 if `databasePrerequisites.ready` false, else 200 `{ready:true}` if DB healthy (:1180-1200). `GET /api/health/live`: 200 `{alive:true,timestamp}` (:1203-1205).
- `GET /api/queue/metrics` (:1208): no auth middleware on the route; exposes queue metrics.
- All of the above have no auth; all under `/api/` pass the general limiter except ready/live.

## Flags
- BUG: `getHealthStatus()` never queries the database; it always returns `healthy:true` unless reading `pool.totalCount` throws, and `responseTime` is computed as `Date.now()-start` immediately (~0) (backend/config/database.js:381-392). `/api/health/ready`, `/db`, `/enterprise` therefore do not detect a DB outage.
- BUG: with the dummy pool (database.js:135-149), `pool.totalCount` is undefined but `getHealthStatus()` still returns `healthy:true` with undefined counts (:381-392). In practice the app does not get that far: the dummy pool's `query` throws, so `testConnection` fails 5 times (database.js:171-208), `initialize()` rethrows (:343-361), `initializeDatabase` rethrows (di/bootstrapper.js:137-149) and `startServer` exits with `process.exit(1)` (server.js:14066, :14211). The exit happens at DB init, before the prerequisite query.
- BUG (timing): `initializePool()` is called fire-and-forget at require time (database.js:153) and awaits `validateDatabaseConfig()` before assigning `pool` (:98-101), so `pool` is `undefined` (:90) until that async init finishes. `testConnection` uses `pool` directly (:176), so an early attempt can hit `undefined.query`; it is caught and retried like any other failure (:182-197). The same delay governs when the dummy pool is installed (:138).
- BUG: Helmet is never applied. It is registered inside an async IIFE after `await getAllSecretData()` (server.js:435-494). Module top-level code is synchronous, so `app.use(helmet)` runs after every route, the 404 handler and `errorHandler` are already registered (:14030-14041); requests are answered before reaching it, so Helmet headers and the CSP are not sent. If `getAllSecretData()` throws, Helmet is never installed at all (:490-492). (Listed as SECURITY as well.)
- BUG: comments contradict values: `max: 500 // Limit each IP to 100 requests` (server.js:645); `RATE_LIMIT_MAX ... // 100 requests per window` default 500 (environment.js:20).
- BUG: CORS allowed methods omit `PATCH` (:550) while the profile-api proxy handles PATCH bodies (:13992).
- BUG: a CORS rejection returns 500 `INTERNAL_ERROR` instead of a 4xx (server.js:547; errorHandler.js:85-101).
- BUG: `module.exports = { pool, ... }` in database.js exports `pool` at module load, when it is still `undefined` (:90, :410-420); consumers using `database.pool` get undefined. Other uses go through functions. Needs consumer check.
- BUG: `transaction()` uses `pool.connect()` without `initializePool()` awaited (:264-265), unlike `query` (:219).
- BUG: productionBootstrap.js indentation shows the `if (!isApiReady())` block closing early (:96-109); behaviour is correct but formatting is broken (cosmetic).
- BUG: `/api/health/live` through the bootstrap before ready returns text, after ready returns JSON, so the probe body changes (productionBootstrap.js:97-100 vs server.js:1203).
- BUG: `healthCheckRoutes` router `GET /` is shadowed by `app.get('/api/health')` (server.js:1033 before :1038-1039), so its queue-health response is never served (healthCheckRoutes.js:31-50).

- SECURITY: `StrictHostKeyChecking=no` in the deploy SSH (prod-deployment.yml:23).
