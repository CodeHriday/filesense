### FE /auth/callback (OktaCallback)
- Trigger: browser redirect from Okta; route exists ONLY in the unauthenticated tree (App.jsx:485). Component src/pages/OktaCallback.jsx. Runs once per mount via a `hasProcessed` ref (:15-26).
- Auth: none (route is unauthenticated by design).
- Inputs: `code` query param and `pkce_verifier` from localStorage; missing either throws 'Missing code or verifier' (:31-37). The `state` query param is never read or compared (:31-33).
- Flow: POST `${OKTA_DOMAIN}/oauth2/default/v1/token` from the browser with grant_type authorization_code (:44-57); GET `.../v1/userinfo` with the Okta access token (:67-70); then POST `${BACKEND_URL}/api/auth/okta/user` with `{okta_id: userInfo.sub, email, username: preferred_username || email, full_name}` and NO Authorization header and NO Okta token (:80-89).
- Outputs/side effects: stores `token` = `authData.tokens.accessToken` and `currentUser` = JSON of `authData.user` in localStorage (:97-98); calls `oktaLogin(authData.user)` which only dispatches AUTH_SUCCESS (:99; AuthContext.jsx:243-245); removes `pkce_verifier` only on success (:101); navigates to `/` (:102). No `refreshToken` is stored (only `tokens.accessToken` is read, :97). `currentUser` in localStorage is never read back (AuthContext bootstrap reads only `token`, AuthContext.jsx:118).
- Errors: any failure is shown as raw text `Error: <message>` including the Okta/backend response body (:62, :74, :93, :120).
- Server side (cross-reference AUTH): server.js:10237 `app.post('/api/auth/okta/user', async (req, res)` has no authenticateToken; it requires only `okta_id` (:10241-10243), looks up `users WHERE okta_id = $1` (:10247) and otherwise inserts a new user with a random password and `auth_provider 'okta'` (:10254-10265), with the client-supplied username and email and a role named User or Executor (:10273-10282). The tail (server.js:10365-10408) generates an access token and a refresh token, stores the refresh token via authService.storeRefreshToken (:10380), and returns the user (without password) and `tokens {accessToken, refreshToken, expiresIn: 30 * 60}` (:10406). The client discards the refresh token, so a live refresh token stays in the DB per Okta login and is never revoked, because logout sends none. A username collision on insert gives a 500 (:10409-10413).

### Axios interceptors (AuthContext and auditInterceptor)
- Trigger: every axios call in the SPA (global `axios` instance); registered in an AuthProvider effect (AuthContext.jsx:330-383) and by initializeAuditInterceptor (auditInterceptor.js:5-51).
- Order: AuthProvider's effect (a child) runs before App's effect (the parent) that calls initializeAuditInterceptor (App.jsx:250-252), so the refresh interceptor is registered first and runs before the audit interceptor. A successful retry therefore suppresses the audit row. When the refresh interceptor rejects, the audit interceptor still posts for 401/403 errors.
- Request interceptor: sets `axios.defaults.baseURL = API_BASE_URL` (:332) and attaches `Authorization: Bearer <localStorage token>` to every request when a token exists (:335-341).
- Refresh interceptor (:349-377): skipped while `isInitializingRef.current` (:355). On status 401 OR 403 (:360) and `!originalRequest._retry`, it sets `_retry`, calls refreshAccessToken() (POST /api/auth/refresh with the stored refresh token, :281-293) and replays the request with the new token (:366-371). So every permission-denied 403 also triggers a token refresh. There is no single-flight guard: each failing request calls refreshAccessToken independently. The refresh endpoint is not excluded from this interceptor.
- Server rotation: the server rejects a used refresh token. authService.refreshAccessToken revokes the old token (authService.js:318) and getRefreshToken filters `is_revoked = FALSE` (authService.js:133-134), so a second use returns `{success:false, 'Refresh token expired or revoked'}` and server.js:10817-10819 answers 401. With parallel requests that all read the old refresh token before a sibling stores the new one (the client stores a returned `tokens.refreshToken`, AuthContext.jsx:302-304), a forced logout is likely, but not certain.
- refreshAccessToken: no stored refresh token returns null with no logout (:284-287). On catch outside initialization it clears both tokens and dispatches LOGOUT (:314-325). However the refresh POST uses the global `axios.post` (:291), so it passes through the same response interceptor; a 401 from /api/auth/refresh has `_retry` unset on this new config, so the interceptor sets it and calls refreshAccessToken() again (:360-364) before the outer catch runs. Read from the code, not run: with a dead refresh token this looks like a runaway chain of POST /api/auth/refresh requests; LOGOUT is reached only when a nested failure is not a 401 (for example a network error), or when a nested call succeeds (a sibling stored a new token) and the retried refresh POST then fails with `_retry` set. Okta sessions store no refresh token (see /auth/callback), so after the 30 min access token expires (server.js:10406) refresh returns null, the request fails with 401/403, and the user is not logged out by this code (only by InactivityTimer or a failed /me on reload).
- Audit interceptor (auditInterceptor.js): module-level once flag (:3, :6-8). Skip list: '/api/audit/frontend-api-error', '/api/auth/login', '/api/auth/logout' (:14). For every other failed request (any status incl. 0 for network errors) it POSTs /api/audit/frontend-api-error with endpoint, method, status code (0 if no response), error message, page URL/title, browser info, and `metadata.request_data` / `response_data` (:27-39, :41). Both bodies are truncated to 500 characters (:36-37). :36 calls `JSON.parse(JSON.stringify(data)).substring(0, 500)`. Axios 1.x (package.json:45) serialises JSON bodies before dispatch, so `error.config.data` is normally a string; `JSON.parse(JSON.stringify(str))` returns the string and the first 500 characters of the raw JSON body are posted, including passwords or tokens in non-login calls (relies on axios 1.x behaviour, not run). Only non-string bodies (FormData, Blob and similar) make :36 throw a TypeError, which is caught at :42 so no audit row is posted for that failure. `originalRequest.url.includes` (:16) is outside the try block.
- Server: /api/audit/frontend-api-error and /api/audit/frontend-error require authenticateToken (server.js:5765, :5671), so errors before login, or after token loss, are rejected and never recorded.

### SPA authorization (client side)
- Routes: no route in App.jsx calls hasPermission or hasRole; every route is a bare ProtectedRoute (authentication only). The AuthContext helpers (hasAdminLevelAccess, hasPermission, hasFeaturePermission, hasRole, hasWritePermission, hasExecutePermission, hasTagPermission; src/context/AuthContext.jsx:39-752) are not applied to routes.
- hasAdminLevelAccess: true only for a roles array containing 'Admin' or 'admin' (AuthContext.jsx:39-51).
- hasPermission (:386-477): false with no user; admin-level users get everything (:386-394). Otherwise exact string match, then split on ':' (or '_', or a bare name read as `:read`), tries resource variations (same, minus trailing s, plus s, dash/underscore swaps) and accepts action equality or '*'. It does NOT let write satisfy read. Object permissions are matched via name, permission_name or permission_code.
- hasFeaturePermission (:480-541): any action other than 'view' becomes 'write' (:491). A permAction of 'write' or '*' satisfies any request, including 'view' (:526, :533). Extra aliases: file_upload gets file and files; quality_checks gets quality.
- hasRole (:544-590): legacy numeric role_id 1/2/3 maps to Admin/Creator/Executor (:552-566).
- hasWritePermission and hasExecutePermission use hasRole('Admin') (:599, :669), not hasAdminLevelAccess. A user with legacy role_id 1 and no 'Admin' in roles is admin for write/execute but not for hasPermission.
- isWriteAction = write, create, update, delete, edit or '*' (:626-628).
- hasTagPermission (:712-752): `tag:<type>:<action>`, case-insensitive type, '*' accepted, and edit implies read only when the request is 'read' (:740-742).
- Sidebar (src/components/Sidebar.jsx:63-149): isVendorOnly = isVendorUser(currentUser) && roles.length === 1 (:64-66). Vendor-only users see only vendor_file_upload, vendor_file_quality, vendor_agreements, vendor_management (:93-96) and file_drop is forced into the sidebar (:138-140). Everyone else is filtered by `<featureId>:read` through hasPermission, with child -> parent fallback and parent visible if any child is readable (:99-130). The no-user Login-link variant (:69-85) is only reachable if Sidebar renders without currentUser, which App.jsx:332 prevents (UNCLEAR if rendered elsewhere). The server does not receive or verify any Okta token, finds the user by `okta_id` (or auto-creates one, :10254-10265) and issues SPA tokens. Anyone who can call the endpoint and knows or guesses an existing user's `okta_id` obtains a session for that user. Cross-reference AUTH.
